## D025 — The Index searches on the server and also takes over the library screens
- Date : 2026-11-27 (committed in 2b772f5, tests in 177f66f)
- Contexte : after trying the Index (D024, deployed b35cfca) the maintainer asked for pagination, to avoid too long loading by fetching only what is needed from Jellyfin instead of everything, and, the classic library screens being unchanged, asked whether the same was planned for them. D024 loaded every item of its list in the browser.
- Décision (assistant's implementation; the maintainer asked for the pagination and the library screens) : the search moves into the plugin, `POST CustomMetadata/Index` (any signed-in user). It reads an in-memory snapshot of the library's video items, taken READ ONLY from Jellyfin's database through `IDbContextFactory<JellyfinDbContext>`; the ids a user may see come from `ILibraryManager.GetItemIds` with that user, watched states are read at each request. It filters, counts, orders and answers ids only; the browser reads the page's items, 60 at a time, from `/Items`. The Series, Episodes and Films views of a library (experimental and classic layouts) are the Index too; the other views stay jellyfin-web's (the experimental screen links to them).
- Alternatives écartées (set aside by the assistant, not discussed with the maintainer) : native `/Items` pagination only → P024; everything kept loaded in the browser → P025.
- Conséquences : amends D024: the library tabs no longer stay stock for these three views and the « Tous les filtres » library link (`pj=index`) is removed; the « anchor » sent to the server, the filtering in the browser and the second pass for people are replaced by server filtering (genres, tags, studios, people still combine with AND; years, playback states and the letter with OR). The snapshot is rebuilt on request, after library events at most every 20 s and at least every 10 minutes, so an edit can take up to 20 s to show in counts; a user's visible ids are kept up to 60 s. An API key (no user) gets 400; a view grouping several libraries gets 404 and keeps the stock screen. The reading depends on Jellyfin's 10.11 database entities (D001): check them on a server upgrade. The stock page hidden under the screen still loads its own first items. Nothing is ever written to the database (D005).

## D020 — The theme's hover preview of a real episode prefers its source's preview video, proxied by the plugin, over its own file
- Date : 2026-11-26 (maintainer decision; uncommitted at the time of writing)
- Contexte : with D019 only missing episodes had a real video preview (their preview trailer); an episode that has its file got trickplay tiles at best, while the source often provides a short preview video for it.
- Décision : on hover, a missing episode plays its trailer; a real episode plays its source's preview, else its own file only if its bitrate is ≤ 12 Mb/s, else trickplay (sharpest set, stepped progress). The source preview comes from `EpisodePreviewService`: season = tag of the file's folder, entry key = the file's first tag, URL from the season's episode list via `PreviewMapper.ResolveUrl`, list cached 30 min per season (local sources included). `PreviewController` `GET CustomMetadata/Preview/{itemId}` (`[Authorize]`, `api_key` in the URL because a `<video>` tag sends no token header) streams it with the source's headers (`SourceHeaders.Apply`) and forwards `Range`; 404 when there is none. Previews keep their aspect (contain) and drop the missing/watched dimming while playing.
- Alternatives écartées : attaching the preview as a Jellyfin trailer on real episodes too → `RefreshExtras` rebuilds `ExtraIds` from disk, and `-trailer` files attach to every episode of a shared folder (docs/architecture/missing-episodes.md); always playing the episode's own file → a Blu-ray/4K file costs tens to hundreds of MB per hover, hence the 12 Mb/s cap; the browser fetching the source URL directly → [supposé] the source's headers/API key would have to reach the browser, and a local source's loopback URL would not be reachable from it.
- Conséquences : every source preview is proxied through the Jellyfin server (bandwidth, one upstream request per hover). A preview URL needing cookies or redirects the proxy does not handle simply falls back to the file/trickplay. The route needs a signed-in user.

## D009 — A missing episode keeps its own number; a clash with a real episode moves it to season number -1
- Date : 2026-11-23
- Contexte : Jellyfin 10.11.6 `SeriesMetadataService.RemoveObsoleteEpisodes` (every series refresh) groups the series' episodes by `ParentIndexNumber` and deletes a virtual episode with no number or whose number a real episode of the same group holds. All seasons without a season number share the null group, so a real `Clip 09.mkv` in another unnumbered season deleted missing episode 9. Earlier plugin versions renumbered the virtual episode, then told the user to number the season folder (P003); the maintainer rejected both: the number typed in the list must win, with no workaround on their side.
- Décision : a missing episode always keeps its number from the list (local source or API). When a real episode of its group holds that number, the virtual episode gets `ParentIndexNumber = -1` (`SeparateGroupSeasonNumber`), and goes back to the season's number once the number is free. Only a number given twice by the list still moves the second episode to the next free number.
- Pourquoi -1 : no real episode ever has a negative season number (own group, never deleted); `AiredEpisodeOrderComparer` counts null as -1, so it sorts exactly like the other episodes of an unnumbered season; `Series.FilterEpisodesBySeason` also matches on the parent season, so it stays listed in its own season only; jellyfin-web shows "Saison locale - 9. Neuf".
- Alternatives écartées : renumbering (huge numbers, then behind the other unnumbered seasons) + asking for a season number in the folder name → P003; a positive unused season number → P004; renaming the user's season folders, or a season-number field in the plugin → both touch the user's seasons.
- Conséquences : `CustomEpisodeProvider` returns the assigned episode AND season numbers for a virtual episode, so a Jellyfin refresh keeps them ([vérifié] in the 10.11.6 source: `MetadataService.MergeData` copies the provider's `ParentIndexNumber` when replacing all metadata, so a null there would put the episode back in the null group, where it gets deleted).
- Liens : motivée par P003, P004
- Code : Services/MissingEpisodeService.cs (`SeparateGroupSeasonNumber`, `AssignIndexNumbers`, `ComputeIndexNumbers`, `EnforceNumbersAsync`, `TryGetAssignedNumber`); Providers/CustomEpisodeProvider.cs; tools/ui-test/missing-number-real.mjs; docs/architecture/missing-episodes.md. Commit 41544ee (2026-11-23); replaces the renumbering of commits 4ba6180, 9d7d312, f3e7c13 [vérifié, commit bodies read 2026-11-24]; the provider-side enforcement of the chosen number started in b296b42.
- À réévaluer si : a Jellyfin upgrade changes the `RemoveObsoleteEpisodes` grouping, the episode sort comparer or `FilterEpisodesBySeason`, or jellyfin-web starts showing the negative season number.
- Fiabilité : [vérifié] missing-number-real.mjs (two unnumbered seasons, full series refresh with replace-all metadata) ALL PASS; display checked on the bench. [vérifié] the Jellyfin internals above, read in the 10.11.6 source (`SeriesMetadataService.RemoveObsoleteEpisodes`, `AiredEpisodeOrderComparer`, `Series.FilterEpisodesBySeason`, `LibraryManager.FillMissingEpisodeNumbersFromPath`).
